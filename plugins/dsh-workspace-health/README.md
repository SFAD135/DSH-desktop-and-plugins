# dsh-workspace-health

在设置里列出一个会话的工作目录已经不可用的情况——也就是「删掉工作区」留下的那个悬空状态。

## 它报告的是什么

`WorkspaceRegistry.delete()` 的文档写得很明白：

> **Delete one workspace registration while retaining its directory and every
> session log.**

删除工作区**只移除注册记录**，目录和会话日志都保留。这是刻意设计。

但会话的 `cwd` 是写死在它自己日志里的持久事实，**永远不会被改写**。所以删掉工作区后，
原先住在里面的每个会话都还指着那个路径。如果目录随后真的消失了，**没有任何地方会说出这件事**。

用户实际撞见的症状很安静、也很难懂：

- 会话照常打开，看起来一切正常；
- 某个工具碰到那条已经不存在的路径时才报错，而**报错只会提到那个文件**，不会提到真正的原因；
- 或者更糟——一次写入悄悄把目录又建了出来，而没有任何工作区认领它。

这个插件把原因指出来。它把**工作目录已不可用的会话**列出来，并**按目录分组**——
一个被删的目录通常困住好几个会话，而它们只需要修一次。

## 检测为什么既便宜又确定

会话存储本来就知道每个会话的 `cwd`，不需要新增任何记账：
`sessionPersistence.list()` 会报告**每一个已存储的会话**——已落盘的产物，
加上本进程创建但尚未落盘的会话。

**这里刻意没有读 `WorkspaceRegistry.headers`**，尽管那张表是公开的、看起来是最显然的来源。
原因是 `headers` 由**启动时一次性建立的索引**（`replaceHeaderIndex`）填充，
再叠加 live session 服务报告的内容；因此**索引建立之后才出现的会话**
（也就是委派出来的子代理会话、以及 seeded 会话）**从不出现在里面**。

在开发这台机器上实测：恰好那两个会话在 `headers` 里缺席、却实实在在存在于磁盘上。
如果照 `headers` 写，这个页面就会**恰好漏掉用户最难自己找到的那类会话**。

**一个细节**：探测用的是 `statSync(path).isDirectory()`，**不是** `existsSync`。
`existsSync` 对一个普通文件也返回 true，而一个指向文件的 `cwd`
和「目录不存在」一样坏。这也正是分类结果有三种而不是两种的原因：

| 代码 | 含义 |
|---|---|
| `live` | 目录正常（不会出现在页面上） |
| `missing` | 路径不存在，或存在但无法解析（权限、断掉的挂载点） |
| `not-a-directory` | 路径存在，但不是目录 |
| `no-cwd` | 会话 header 里根本没记录工作目录 |

## 数据怎么从 host 走到浏览器

渲染这个页面的半边跑在浏览器里，**碰不到文件系统**，所以判断必须由 host 传过去。

dsh 的 Remote 绑定是**构建期生成**的（`typert.host.js` / `typert.remote-client.js`，
各自带着 schema 和源码位置），新增 RPC 就意味着改生成文件，而下一次 dsh 升级会覆盖它。

所以两个半边在本插件自己的 settings 命名空间里会合——走的正是 `dsh-session-prompt`
和 `dsh-archived-sessions` 都在用的官方通道 `settings.describe` / `settings.mutate`。

**只有结论跨过半边**：标题和路径不传输，因为设置外壳本来就会把 `useSessions`
快照选择器交给 `settings.section` 的条目，页面读的就是侧边栏读的同一个投影。

**发布是变化驱动的**：扫描按定时器跑，但只有结论**真的变了**才调用 `scope.replace()`。
所以稳态下**一次写盘都没有**，settings 文件不会每十秒被重写一遍。

## 两个展示面

### 一、左侧栏标红

工作目录不可用的会话，在左侧栏里**整行显示为红色**，鼠标悬停显示
「当前会话工作区不存在」。这是用户实际浏览的界面，所以它回答了
「那个会话为什么突然坏了」而不用打开任何东西。

**它怎么知道哪一行是哪个会话**——这是整个插件最脆弱的一环，必须说清楚：

会话行的 DOM **不带任何标识**。`SessionNodeItem` 渲染的 `div` 只有
`role="treeitem"`，没有 `data-*`，没有能用的 `aria-label`，
而 `node.id` 只用作 React 的 `key`——**`key` 不会落到 DOM 上**。

所以只能从 React 里读回来：React 给每个由它创建的 DOM 节点挂了一个
`__reactFiber$…` 反向引用。从这一行往上走 `return`，就能到达
`SessionNodeItem` 的 fiber，它的 `memoizedProps` 里就是会话节点。

`role="treeitem"` 被**三种**不同的行共用，不能随便取第一个遇到的组件，
判据是只有会话行才同时具备的两个 prop：

| prop | 为什么能区分 |
|---|---|
| `node` | 工作区行拿到的是 `group`，搜索结果拿到的是 `result`，都没有 `node` |
| `onOpen` | 工作区行没有 `onOpen`；搜索结果**有**——这正是必须同时要求 `node` 的原因 |

属性名按**前缀**匹配，所以 React 换掉随机后缀不影响；但如果哪天彻底不再挂这个属性，
标红就会停止工作——**后果就是恢复到这个文件存在之前的样子，不会弄坏任何东西**。

### 二、设置页

- 顶部说明这个状态是怎么来的；
- `N 个会话的工作目录不可用，分布在 M 个目录下。`
- 每个目录一组，组头是**目录路径**加一个原因标签，下面是该目录下的会话标题；
- 没有问题时显示「所有会话的工作目录都在。」

两个展示面**共用同一次轮询**：`apply` 拉一次 `settings.describe`，再广播给两边。
标记的样式走一张注入的 `<style>`，锚点用 `role="treeitem"`（语义属性，
CSS module 改名动不了它）加上插件自己设的 `data-dsh-orphan`。

DOM 监听只订阅 `childList` / `subtree`，**故意不订阅 `attributes`**——
因为标红这个动作本身就在写属性，订阅了就变成每次标记都触发新一轮标记。
一轮标记还被合并到下一个动画帧，避免滚动时的抖动。

## 怎么修

页面上只报告，不提供「修复」按钮——因为每条修法都涉及真实文件系统操作，
让用户自己决定更稳妥：

- **目录还在**（只是工作区注册没了）：在 DSH 里重新添加该目录为工作区；
- **目录真的没了**：把目录恢复出来，或接受这些会话已经无法继续；
- **想把会话收起来**：用 `dsh-archived-sessions` 的「已归档会话」页。

## 安装 / 卸载

```powershell
powershell -ExecutionPolicy Bypass -File install.ps1
powershell -ExecutionPolicy Bypass -File uninstall.ps1
```

默认使用 `$env:DSH_HOME` 与 `web` profile，可用 `-DshHome <path> -ProfileName <name>` 覆盖。

安装后**刷新一次 Web GUI**，设置里会出现一个标着「工作区健康」的页面。
（host 半边会随补丁层热挂载，但浏览器半边需要一次页面加载才会注册。）

## 改过 host 代码就必须重启桌面端

这一条踩过坑，写下来备查。

host 半边的代码由 **Node 的 ESM 加载器**加载，而模块缓存**不会**因为磁盘上的文件变化而失效。
所以把新的 `lib/index.js` 部署上去之后，**运行中的进程仍然在执行旧模块**：

- **补丁层的增删**（新增/移除一行 `insert`）会触发插件的重新挂载；
- 但重新挂载时对同一路径的 `import()` 拿到的是**缓存里的旧模块**，不是新文件。

实测：改完代码重新部署，等了两个扫描周期又手工触发了一次补丁层变化，
`settings.yaml` 里的结果**纹丝不动**。

结论：

| 改了什么 | 需要做什么 |
|---|---|
| `lib/index.js`（host） | **重启桌面端** |
| `lib/client.js`（浏览器） | 刷新页面 |
| `cordis.patch.yml` 的增删 | 通常热生效 |

## 校验

```powershell
node verify.mjs     # 95 项离线检查
```

需要目录下有一个指向 dsh 运行时的 `node_modules` junction（用来解析
`@deepseek-ai/schemastery` 以及加载 client 半边）；仓库里的开发副本就带着一个。
`install.ps1` **只复制本包实际发布的文件**，绝不整目录复制，所以这个 junction 不会被装进 profile。

覆盖五组断言：

- **分类**：目录 / 普通文件 / 不存在 / 无 cwd，既有注入式探针，也有一次真实文件系统对照；
- **扫描**：只有不可用的会话被报告；空表、缺输入、null header、无 id 的 header 都不炸；
- **发布**：首次发一次；结论不变**不重发**；结论变化才重发；写失败会重试而不是把页面钉在旧结论上；
  **列举失败时一条都不发**——因为存储打嗝就把每个会话都报成坏的，比什么都不报糟糕得多；
- **分组**（client 半边）：按目录分组、按路径排序、未知 cwd 排最后、标题回退、
  以及 `remote.settings` 必须出现在 `inject` 里这个回归点；
- **侧边栏标记**（client 半边）：用假的 fiber 链验证会话 id 能读出来、
  三种 `treeitem` 不会互相误判、**缓存不记未命中**（否则那一行会永远标不上）、
  标记的幂等与撤销、以及样式表确实锚在语义属性上。
